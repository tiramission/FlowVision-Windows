## 0. 结论

查看器“加载挺久”的主因不是解码，而是**把整图解码后，用 `draw.CatmullRom` 在 Go 里缩到 2560，再编码成 JPEG**。冷开实测 0.87–1.43 秒，其中缩放占 60–78%。

优先级最高的四件事：

1. **2560 预览改用 `draw.ApproxBiLinear`**：缩放从 571–885ms 降到约 95ms，冷开可到 0.3–0.4 秒；真实照片质量 PSNR 40–49dB，合成渐变图 31.9dB，需做视觉门禁。
2. **直接 `ui.NewBitmap(dst)` 上屏**：不再为了首屏先编码 JPEG 再 `ui.DecodeBitmap`，再省 60–150ms；JPEG 缓存异步写盘。
3. **打开瞬间先用网格缩略图占位**：当前 `viewer.Bitmap` 被置空，只能显示“正在载入…”；改成缩略图先画，2560 到位再替换，首帧从空白变成立刻有图。
4. **修 preload 优先级反转**：`previewBytes` 先锁 `previewMu` 再查缓存，preload worker 可能拿着锁生成邻居；当前图会排队。缓存检查移出锁、当前图完成后再启动 preload。
5. **全量补齐原可选项**：悬停预取、1:1 全分辨率按需查看、非侵入式状态提示（HUD）全部纳入 Phase 4 必做；补 20 张真实相机 JPEG 语料，不再设“如时间允许”。

不建议为查看器继续走 WIC 2560：实测 WIC 生成 2560 预览 0.8–1.26 秒，没有优势，瓶颈是高质量缩放和编码，不是解码器不够快。

## 1. 现状与根因

### 1.1 当前链路

| 步骤 | 代码 | 行为 |
|---|---|---|
| 打开 | `openViewer` / `loadViewerMedia` | `viewer.Bitmap = nil`，异步 `decodeViewerImage`；加载期间显示“正在载入…” |
| 取预览 | `decodeViewerImage` → `previewBytes` | 先查 `%s-preview-Mtime-Size.jpg` 磁盘缓存；未命中则整图解码 |
| 解码 | `image.Decode` | 24MP/48MP JPEG 全部解到内存，未按 2560 降采样 |
| 缩放 | `scaleImage` = `draw.CatmullRom.Scale` | 高质量 Catmull-Rom，2560 输出耗时 571–885ms |
| 编码 | `jpeg.Encode` q90 | 2560 JPEG，61–102ms，文件约 0.7–2.2MB |
| 上屏 | `ui.DecodeBitmap` | 又把刚编码的 JPEG 解码成 bitmap，约 44ms |
| 预加载 | `viewer_preload.go` | 默认前后各 2 张，单 worker；结果存 2560 bitmap，约 17MB/张 |

关键代码事实：

- `previewBytes` 用全局 `previewMu` 串行化所有预览生成；这是 4GB 机器上的内存保护，但会造成当前图与预加载抢锁。
- `loadViewerMedia` 在启动当前图的解码 goroutine 后立刻 `scheduleViewerPreload()`，preload 可能先拿到 `previewMu`。
- `previewBytes` 在 `previewMu` 内才 `readFreshCache`，即使当前图有缓存，也要等 preload 的整图解码结束。
- 查看器只生成最长边 2560 的预览，不是原图；`viewerActualSize` 的 100% 也基于 2560 bitmap。
- `ViewerPreload` 默认 2，范围 0–8；8 时最多约 9 张 2560 bitmap，约 150MB。
- `clearViewerPreloadCache` 只清 map，没有显式 `ReleasePixels`；需要在本次一并收紧所有权与释放。

### 1.2 已测基线

测试语料：`testdata/thumb-corpus` 的 24MP 合成 JPEG、真实 Picsum JPEG；本地 4GB 内存机器，冷缓存，串行单张。

| 场景 | 实测 |
|---|---:|
| 24MP `previewBytes` 冷生成 | 1.13s |
| 真实 12–16MP JPEG 冷生成 | 0.87–1.19s |
| 24MP 解码 | 184.7ms |
| 24MP CatmullRom 缩到 2560 | 885.2ms |
| 真实 12MP 解码 | 193.0ms |
| 真实 12MP CatmullRom 缩到 2560 | 571.4ms |
| JPEG q90 编码 | 61–102ms |
| 预览缓存命中读取 | 0.58ms |
| 缓存命中后 `ui.DecodeBitmap` | 44.4ms |

### 1.3 已做的预研结论

| 方案 | 结果 | 判断 |
|---|---|---|
| `draw.ApproxBiLinear` 缩到 2560 | 约 95ms，CatmullRom 约 989ms | **首选**，快约 10x |
| ApproxBiLinear 质量对比 | MAE 0.57–2.42；PSNR 31.9–48.6dB；真实照片 40–49dB | 需视觉门禁，默认可用 |
| `draw.BiLinear` | 约 909ms | 不采用，精确双线性不比 CatmullRom 快 |
| `draw.NearestNeighbor` | 约 67ms | 速度好但锯齿明显，不采用 |
| WIC 2560 预览 | 0.80–1.26s | 不采用，无优势 |
| `ui.NewBitmap` 直接上屏 | API 已存在，测试中使用 | 可作为正式路径；需测创建成本与所有权 |

## 2. 目标与验收

### 2.1 性能目标

测试条件：本地 SSD，冷预览缓存，24MP 基准 JPEG；另测 48MP、真实照片、PNG/WebP。数值为单张首开，不含用户点击前的网格时间。

| 场景 | 当前 | 目标 P50 | 目标 P95 | 冲刺 |
|---|---:|---:|---:|---:|
| 首帧可见（占位图） | 空白 | ≤ 50ms | ≤ 80ms | ≤ 30ms |
| 24MP 冷开 2560 清晰图 | 0.87–1.43s | ≤ 450ms | ≤ 700ms | ≤ 350ms |
| 48MP 冷开 2560 清晰图 | 未单独测 | ≤ 900ms | ≤ 1.2s | ≤ 750ms |
| 24MP 1:1 原图首帧（按需） | 未单独测 | ≤ 600ms | ≤ 900ms | ≤ 500ms |
| 48MP 1:1 原图首帧（按需） | 未单独测 | ≤ 1.2s | ≤ 1.8s | ≤ 1.0s |
| 预览缓存命中打开 | 44ms | ≤ 80ms | ≤ 120ms | ≤ 60ms |
| 已预加载的上一张/下一张 | 未单独测 | ≤ 100ms | ≤ 150ms | ≤ 60ms |
| 连续 10 次快速切换 UI 阻塞 | 未单独测 | 无 >100ms 卡顿 | 无 >150ms | 无 >80ms |
| 查看器打开后 Private（2560） | 约 479–493MB（含网格） | ≤ 650MB | ≤ 750MB | ≤ 600MB |
| 查看器打开后 Private（24MP 1:1） | 未单独测 | ≤ 800MB | ≤ 900MB | ≤ 750MB |
| 查看器打开后 Private（48MP 1:1） | 未单独测 | ≤ 1.0GB | ≤ 1.2GB | ≤ 950MB |
| 50 次打开/关闭内存增长 | 未测 | ≤ 30MB | ≤ 50MB | ≤ 20MB |

### 2.2 质量目标

- 2560 预览与当前 CatmullRom 结果对比：真实照片 PSNR ≥ 38dB、MAE ≤ 1.5/255；合成渐变图 PSNR ≥ 30dB、MAE ≤ 3/255。
- 对比图不得出现明显锯齿、摩尔纹、光晕、色偏；人像皮肤、文字截图、细密纹理单独检查。
- EXIF Orientation 1–8 正确；透明图仍按查看器黑底/原有合成逻辑显示。
- JPEG baseline/progressive、PNG、WebP、TIFF、BMP、GIF 不回归；HEIC/RAW 仍走原有失败占位，不在本次新增 codec。
- 2560 预览仍是默认首屏；1:1 原图按需加载（用户点击“实际大小”或 Zoom ≥1.25），属于 Phase 4 必做，不改变默认打开行为。
- 1:1 只在 ≤50MP 的单图上启用；>50MP 仍显示 2560 预览并在信息面板提示，避免 4GB 机器被单张 bitmap 拖垮。

### 2.3 非目标

- 不重做网格缩略图（`v1.3.0` 已收尾）。
- 不把查看器改成 tile/分块查看器。
- 不为 2560 预览引入 WIC 高质量缩放（实测无优势）。
- 默认打开不加载全分辨率原图；1:1 只在用户触发时按需加载。
- 不改变视频播放链路。
- 不自动发布；版本与 Release 需另行确认。

## 4. Phase 0：基线与 profiling

### 4.1 计时埋点

在 `debug.go` 的 viewer 状态中增加：

- `viewerLoadMs`：从 `openViewer` 到首帧 bitmap 可用。
- `viewerCacheHit`：本次是否命中 2560 预览缓存。
- `viewerDecodeMs` / `viewerScaleMs` / `viewerEncodeMs` / `viewerBitmapMs`。
- `viewerPlaceholderHit`：是否用网格缩略图占位。
- `viewerPreloadHit`：打开时是否命中邻图预加载。
- `viewerPreloadBytes` / `viewerPreloadCount`。
- `viewerFullResMs` / `viewerFullResBytes`：1:1 按需解码耗时与 bitmap 字节。
- `viewerLoadGen`：防止旧 generation 覆盖新图。

要求：埋点只记录耗时，不改变加载顺序；首版先用 `time.Since` 与字段快照，不做分布式 trace。

### 4.2 语料

复用 `testdata/thumb-corpus`：

- `dirs/24`、`dirs/100`、`dirs/300`：24MP 合成 JPEG，测连续切换与目录压力。
- `real/`：真实 Picsum JPEG，测高熵、progressive。
- `sizes/12mp.jpg`、`sizes/48mp.jpg`：尺寸边界。
- `formats/`：PNG、WebP、TIFF、BMP、GIF、HEIC 失败占位。
- `orientation/`：EXIF 1–8。
- 新增 1 张 80MP、1 张 50MP、1 张 1MP 边界图；50MP 验证 1:1 上限，80MP 只验证预览边界；超过 80MP 改走系统缩略图回退，不再直接拒绝预览。
- 必须补 20 张真实相机 JPEG（含 160/1600px 内嵌预览）作为真实语料，不与 `v1.3.0` 合成基线混用；没有自有相机样张时用公开可商用样张，记录来源与许可。

### 4.3 跑分矩阵

| 维度 | 取值 |
|---|---|
| 冷/热 | 清空预览缓存 / 第二次打开 |
| 尺寸 | 12MP、24MP、48MP、80MP |
| 格式 | baseline JPEG、progressive JPEG、PNG、WebP、TIFF |
| 状态 | 首次打开、上一张、下一张、快速连续 10 次、关闭再开 50 次 |
| 预加载 | `ViewerPreload=0/2/4/8` |
| 内存 | 4GB 机器；记录 Private、Working Set、GDI、Handles |

### 4.4 决策门 0

- 确认缩放占比仍 >50%；如果 Phase 1 后占比降到 <20%，后续只做缓存/调度。
- 确认 `ui.NewBitmap` 创建成本；如果 >50ms，保留 JPEG 编码路径并只换缩放器。
- 确认 48MP 冷开基线；如果 >2s，Phase 1 目标改为先保证 48MP 不崩，再谈速度。

## 5. Phase 1：预览生成快路径

### 5.1 快速缩放

- 新增 `scaleImageFast`，使用 `draw.ApproxBiLinear`。
- 默认 `viewerPreviewScaler=fast`；保留 `FLOWVISION_VIEWER_SCALER=hq` 走 CatmullRom，用于 A/B 和回退。
- 仅对查看器 2560 预览生效；网格缩略图仍用现有 `thumbnailImage`，不改视觉效果。
- 如果质量门禁失败，采用两阶段：先 `ApproxBiLinear` 上屏，空闲 150ms 后用 CatmullRom 重生成并替换；不能直接回退到全程 CatmullRom，否则没有性能收益。

### 5.2 直接 bitmap 上屏

- 新增 `previewImage(it) (*ui.Bitmap, []byte, error)` 或等价接口：
  1. 查 2560 预览缓存；命中则读 JPEG → `ui.DecodeBitmap`，约 44ms。
  2. 未命中：`image.Decode` → orientation → `scaleImageFast` 到 2560 → `ui.NewBitmap(dst)`。
  3. 同一份 `dst` 编码 JPEG q90，异步写缓存；写盘失败不影响上屏。
- 首屏不再走“先编码再解码”的往返；缓存仍保留，第二次打开仍走 44ms 快路径。
- 如果 `ui.NewBitmap` 会复制像素，保留 `dst` 到编码完成；如果引用，必须先编码或做拷贝，严禁在上屏后继续读已释放的像素。

### 5.3 缩略图占位

- `Viewer` 增加 `Placeholder *ui.Bitmap`，与 `Bitmap` 分离，避免把网格缓存的 bitmap 当自有资源释放。
- 打开时按优先级取占位：
  1. 当前网格缓存的 480px（如果用户使用 480 桶）；
  2. 当前网格缓存的 220px；
  3. 没有则保持“正在载入…”。
- `viewerCanvas` 在 `Bitmap == nil && Placeholder != nil` 时绘制占位图；2560 到达后清空 `Placeholder`，不改 `Loading` 文案逻辑。
- 占位图只借不拥有；关闭查看器、清缓存时不能 `ReleasePixels` 网格缓存的 bitmap。

### 5.4 验收

- 24MP 冷开 P50 ≤450ms、P95 ≤700ms。
- 首帧占位 ≤50ms。
- 真实照片质量 PSNR ≥38dB；合成渐变 ≥30dB；无可见锯齿/光晕。
- 缓存命中仍 ≤80ms。

## 6. Phase 2：优先级、缓存与预加载

### 6.1 修优先级反转

- `previewBytes` / `previewImage` 的缓存命中检查移到 `previewMu` 外；只有真正生成时才拿锁。
- `loadViewerMedia` 不再在启动当前解码后立刻 `scheduleViewerPreload`；改为当前图 bitmap 落地后再启动预加载。
- 当前图生成期间设置 `viewer.Loading`/generation 保护；preload worker 启动前检查当前 generation，避免旧任务抢锁。
- 快速上一张/下一张时清空 `viewerPreloadDesired`，已在跑的任务允许完成但不写入新 generation。

### 6.2 预加载预算

- `viewerPreloadBytesMax = 128MB`（暂定）。每个 2560 bitmap 约 17MB；默认 2 张前后各 2 张约 85MB，低于预算。
- 用户把 `ViewerPreload` 调到 8 时，按字节预算裁剪，不一次性保留 9 张。
- 预加载条目记录 `Bytes`，淘汰最远/最旧条目并 `ReleasePixels`。
- `clearViewerPreloadCache` 必须释放所有 bitmap；关闭查看器、切换目录、清缓存三条路径统一。

### 6.3 缓存写入

- 2560 预览缓存保持 JPEG q90；路径含 `maxDim=2560`、质量模式和缓存版本，防止 fast/HQ/旧 2560 混用。
- 写盘用 `tmp + rename`；异步写失败只记录日志，不影响首屏。
- 读缓存继续用 `readFreshCache` 的 mtime/size 校验；源文件改动后旧缓存不得复用。
- `trimThumbCache` 已把预览文件纳入 1500MB 上限；本次不变，但报告中记录 300 张 2560 预览约 300–600MB 的占用。

### 6.4 验收

- 当前图不再等待 preload；最坏打开从“2 段 1s”回到单段 0.3–0.4s。
- `ViewerPreload=8` 时内存不超预算，不触发 4GB 机器提交压力。
- 50 次打开/关闭，Private 增长 ≤30MB，GDI/Handles 不回涨。

## 7. Phase 3：质量、格式与稳定性回归

### 7.1 质量矩阵

- 24MP 合成渐变、真实人像、真实风景、文字截图、透明 PNG、细密纹理。
- 每张同时生成 CatmullRom 与 ApproxBiLinear 2560，记录 PSNR/MAE，并输出并排图。
- 视觉检查：边缘、文字、头发、砖墙、渐变天空；发现摩尔纹则改用“fast 首屏 + HQ 替换”。

### 7.2 格式矩阵

- baseline/progressive JPEG、CMYK、灰度、4:2:0/4:2:2/4:4:4。
- PNG/APNG、GIF、WebP、TIFF、BMP。
- HEIC/RAW 仍按当前系统 codec 状态；无 codec 时占位，不因本次改动崩溃。
- EXIF 1–8；透明图；超大 80MP；损坏/0 字节。

### 7.3 稳定性

- 连续 50 次打开/关闭；连续 20 次上一张/下一张；快速 10 次跨目录。

- 4GB 内存下同时保留网格 300 张 220px 缓存 + 查看器 5 张 2560 bitmap。
- 记录 Private、Working Set、GDI、USER、Handles；不允许持续上涨。

## 8. Phase 4：必做增强（三项全部交付）

### 8.1 悬停预取

- 网格项 hover ≥200ms 时，预生成该图 2560 预览；离开则取消。
- 单 worker、最低优先级；不抢占当前查看器。
- 预期：点击时大概率命中缓存，打开 ≤80ms；代价是后台磁盘/CPU。
- Phase 1/2 稳定后进入；必须实现。4GB 内存或磁盘压力明显时降级为“只预取相邻 1 张”，不关闭功能入口。
- 复用现有 `ViewerPreload` 作为总开关：`0` 同时关闭邻图预取与悬停预取，`>0` 开启；不新增设置项。

### 8.2 1:1 全分辨率

- 当前查看器 100% 实际是 2560，不是原图。本版必须实现真正的 1:1：
  - 只在用户点击“实际大小”或 Zoom ≥1.25 时解码原图；
  - 单张、按需、不预加载；1:1 结果单条 LRU 缓存，字节预算 256MB（24MP 约 96MB，48MP 约 192MB），超预算立即释放；
  - ≤50MP 启用 1:1；>50MP 只显示 2560 预览并在信息面板提示“超过 1:1 上限”；
  - 原图 bitmap 约 96MB/24MP、192MB/48MP，4GB 机器必须过内存门禁。
- 1:1 与首屏优化同版本 `v1.4.0` 交付，不再单独立项。
- 1:1 只做单图按需位图，不做完整 tile/分块引擎；超大图仍受 50MP 门禁保护。

### 8.3 状态提示（HUD）

### 8.4 不建议

- 3840 预览：像素量 2.25x，内存和缩放成本全面上升，收益只对 4K 屏明显。

- 通用通知中心/通知列表/红点：会把查看器变成仪表盘，收益低、打断沉浸。

## 12. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| ApproxBiLinear 在文字/细纹上锯齿 | 预览观感下降 | 质量门禁；fast 首屏 + HQ 替换；`FLOWVISION_VIEWER_SCALER=hq` |
| `ui.NewBitmap` 所有权不清 | 崩溃/花屏/泄漏 | 明确 owned/borrowed；占位图只借；缓存统一释放 |
| 异步写盘与退出竞争 | 临时文件残留 | tmp+rename；启动清 `.tmp-*`；失败忽略 |
| preload 仍抢当前锁 | 最坏 2s | 缓存检查移出锁；当前完成后再 preload；generation 丢弃旧任务 |
| 4GB 内存不足 | 进程消失/卡顿 | 128MB 预加载预算；单张生成；50 次开关门禁 |
| 1:1 巨型 bitmap | 内存峰值/崩溃 | ≤50MP 才进 1:1；单条 LRU 256MB；切图立即释放；>50MP 只预览 |
| 1:1 解码超时 | 点击后长时间黑屏 | 先保留 2560 占位；1:1 到达后替换；超过 1.5s 显示加载提示 |
| HUD 打断沉浸 | 用户分心/遮挡 | 单槽、底部、1.2–2.5s 淡出、不堆叠；默认 auto；可 off |
| 悬停预取抢占资源 | 当前图变慢/磁盘抖动 | 单 worker、最低优先级、只相邻 1 张；压力大自动降级 |
| 旧 2560 缓存与新质量模式混用 | 质量不一致 | 缓存 key 含 maxDim/quality/version；必要时一次性失效 |
| 2560 上限被误解为原图 | 用户预期落差 | README/CHANGELOG 明确默认 2560；1:1 按需并在信息面板标注 |
| 48MP/80MP 内存峰值 | 失败 | 超过 80MP 走系统缩略图回退；48MP 单张；1:1 仅 ≤50MP；测 Private/提交 |

## 17. 查看器非侵入式状态提示（Phase 4.3，必做）

- 结论：**不做通用通知中心**；必须做“单槽状态提示 + debug HUD”。通知会堆叠、打断沉浸，而且查看器已有文件名/序号、缩放百分比和加载文案。
- 定位：状态反馈优先，通知其次。持久信息留在现有 header/footer；瞬时事件用单槽提示；性能数据只在 debug 构建可见。
- 默认策略：`ViewerHUD=auto`，只在用户动作后出现，1.2–2.5 秒淡出；不堆叠、不抢焦点、不挡画面中心；沉浸模式仅在用户主动操作或错误时显示。
- 设置项必须包含 `ViewerHUD`：`off / auto / always`，默认 auto；环境变量 `FLOWVISION_VIEWER_HUD` 仅用于覆盖和诊断。
- 隐私：只做本地状态，不做网络遥测；不默认上报任何查看行为。

### 17.1 事件取舍

| 事件 | 处理 | 形式 |
|---|---|---|
| 当前文件名、序号 | 已有 | header，不重复 |
| 当前缩放百分比 | 已有 | footer；chrome 隐藏时用单槽提示 |
| 切图成功 | 不需要 | 图像本身即反馈；header 序号已更新 |
| 第一张/最后一张 | 必做 | 单槽提示“已到最后一张”，1.5s |
| 加载开始 | 已有 | 现有“正在载入…”；用缩略图占位替代空白 |
| 加载完成 | 不需要 | 图像出现即可；加 120ms 淡入 |
| 加载超过 500ms | 必做 | 显示阶段文案“解码中/缩放中”，不显示假百分比 |
| 加载失败 | 必做 | 错误卡片/提示，保留到关闭或重试，不自动消失 |
| 缩放动作 | 必做 | chrome 可见时 footer 已显示；隐藏时单槽“125%”，800ms |
| 缩放到达上限/下限 | 必做 | 单槽“已到最大 800%”，仅在碰到边界时 |
| 适合窗口/实际大小 | 必做 | 单槽“适合窗口 / 100%”，800ms |
| 预加载命中/缓存命中 | 必做（debug） | 只进 debug HUD，不进普通 HUD |
| 解码/缩放耗时、缓存字节 | 必做（debug） | 只进 debug HUD，不进普通 HUD |
| 大图 2560 预览上限 | 必做 | 信息面板固定说明，不用每次弹通知 |
| 1:1 超过 50MP 拒绝 | 必做 | 信息面板提示“仅 2560 预览”，不弹错误 |

### 17.2 单槽提示规则

- 只有一个 `viewerNotice`，新事件替换旧事件；最多两行，字号 11–12，宽度不超过画布 40%。
- 位置：底部居中、footer 上方 12px；如果 footer 可见则再上移；不覆盖图像中心。
- 颜色：中性深色半透明底，文字高对比；错误用低饱和红，不用大面积色块。
- 时间：缩放/边界 1.2–1.5s；错误 4s 或手动关闭；加载阶段只在超过阈值后出现。
- 节流：滚轮缩放 80–100ms 合并一次；连续 `+/-` 只更新同一个提示，不排队。
- 交互：`IgnoreInput(true)`，不拦截点击/滚轮/快捷键；点击提示可关闭，但不抢焦点。
- 动效：120–160ms 淡入/淡出；不做位移弹跳，避免干扰看图。
- 无障碍：文字可读，不只靠颜色表达状态；错误状态有文字说明。

### 17.3 debug HUD

- 必须实现；仅在 `debug` 构建或 `FLOWVISION_VIEWER_HUD=debug` 时显示。
- 字段：`loadMs`、`cacheHit`、`decodeMs`、`scaleMs`、`encodeMs`、`bitmapMs`、`preloadBytes`、`preloadHit`、`zoom%`、`index/total`、`fullResMs`。
- 位置：右上角或左下角，小字号、半透明；不进入发布截图，不影响普通用户。
- 与 Phase 0 埋点共用字段，避免维护两套统计。

### 17.4 验收门

- 单槽提示必须作为发布默认（auto）通过：沉浸模式 10 分钟连续看图无遮挡投诉；快速切图 20 次不堆叠；`off/always` 均生效。
- debug HUD 必须可开启并输出上述字段，不能只在开发者本机可用。
- 不做通知列表、历史中心、消息红点；这些会把查看器变成仪表盘，收益低、维护成本高。
