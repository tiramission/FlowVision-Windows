# FlowVision Windows 缩略图性能基线

- 日期：2026-11-26
- 基线版本：`v1.2.17` / `d6d8a55`
- 机器：Windows 11 企业版 10.0.26100；Intel Core i7-12700H（10 核 / 20 线程）；4 GB 内存；C: 盘剩余约 56.6 GB
- 语料：`testdata/thumb-corpus`，由 `tools/make_thumb_corpus.py --full` 生成；24 MP 合成 JPEG 4–6 MB/张，真实照片另见 `docs/缩略图测试语料说明.md`
- 口径：本地 NVMe，6 worker，目标缩略图高度 220（缓存桶 240）；先清空应用缩略图缓存；系统文件缓存无法在 4 GB 单机环境彻底隔离，表中是同一轮多次运行的中位数量级

## 1. 旧 Go 路径

`FLOWVISION_THUMB_BACKEND=go`，即 `image.Decode` 整图解码 → 面积平均 / Catmull-Rom → JPEG q84。

| 目录 | 文件数 | 总墙钟 | 单张 | 峰值堆 |
|---|---:|---:|---:|---:|
| `dirs/24` | 24 | 1812 ms | 75.5 ms | 376 MB |
| `dirs/100` | 100 | 7283 ms | 72.8 ms | 419 MB |
| `dirs/300` | 300 | 21287 ms | 71.0 ms | 419 MB |

数据来自 `go test -run TestThumbBaseline`，输出 `docs/thumb-bench-go.json`。这是当前代码的 Go 回退路径，不包含 UI 绘制；v1.2.15 的旧测量为 1734 / 6740 / 20221 ms，量级一致。

## 2. 真实应用首屏

用 debug 构建、单标签启动，清空磁盘缩略图缓存后打开目录，计时从 `open` 命令发出到 `thumbPending=0 && thumbRunning=0`。窗口可见 4 列 × 3 行，首屏 12 张，后续行由预取补充。

| 目录 | 旧 Go 首屏 12 张 | 新 auto 首屏 12 张 | 旧 Go 全部预取 | 新 auto 全部预取 |
|---|---:|---:|---:|---:|
| `dirs/24` | 749 ms | 305 ms | 3243 ms（27 张） | 952 ms（27 张） |
| `dirs/100` | 965 ms | 376 ms | 3110 ms（27 张） | 1002 ms（27 张） |
| `dirs/300` | 686 ms | 374 ms | 2155 ms（27 张） | 998 ms（27 张） |

原始 JSON：`docs/thumb-app-firstscreen-go.json`、`docs/thumb-app-firstscreen.json`。首屏计时到 `ThumbReady=12`（4 列 × 3 行），预取随后继续；全部预取计时到队列清空。旧 Go 首屏只比全量快约 2–4 倍，因为 12 张大图解码仍然昂贵；WIC 的固定 COM 初始化/调度成本在 12 张时占比更高。

## 3. 扫描与 header probe

- `testdata/thumb-corpus/dirs/100` 的 `fillDims(100)`：约 28 ms。
- `probeImageDims` 从每张 JPEG 两次 open 改为一次 open + 复用 128 KiB 头；24 MP JPEG 头探测在亚毫秒级。
- `fillDims` 预算从 900 降到 160；100 张目录不再等待整目录 header 扫描才返回。

## 4. 结论

旧路径的主要成本是整图解码和峰值内存，不是 JPEG 编码。WIC/Shell 后端把单张 24 MP JPEG 从约 71–75 ms 降到约 33–40 ms，峰值堆从约 419 MB 降到 15 MB；真实应用首屏 12 张从 0.69–0.97 s 降到 0.31–0.38 s，全部预取从 2.2–3.2 s 降到 0.95–1.0 s。完整 100/300 张目录的最终数据见 `docs/缩略图性能报告.md`。

## 5. 限制

- 4 GB 内存机器上同时运行 debug 应用和完整 Go 基准会触发系统提交压力；基准和应用验收分开执行。
- 外接 USB HDD、SMB 网络盘、系统文件缓存完全冷启动未在本机复现；这些场景保留为发布后回归项，不把本地 SSD 数字外推成结论。
