# FlowVision Windows 缩略图性能优化完整计划

- 版本基线：`v1.2.17` / `d6d8a55`
- 目标发布：`v1.3.0`（单版本，已确认）
- 日期：2026-11-26
- 状态：已完成（`v1.3.0`，2026-11-26）；Phase 0–6 已执行，结果见 `docs/缩略图性能报告.md`
- 范围：主窗口网格缩略图；不含查看器大图解码、视频缩略图、macOS 源码修改
- 目标：在本地 SSD、外接盘、网络盘上，把大量大图目录的缩略图首屏、完整填充、滚动回看都做到可接受；同时补齐 HEIC/RAW 等格式的系统解码能力

## 0. 结论

当前慢的主因是每张图都走 `image.Decode` 整图解码，再自己缩小；macOS 版走 ImageIO 的系统缩略图接口，在解码阶段就按 512px 上限产出。继续加 worker 或调缓存只能改善边角，不能改变单张成本。

所有方向都做，但角色分开，避免同时维护多套完整解码器：

- **默认路径**：WIC 缩放解码（Windows 上最接近 ImageIO 的路线）
- **首屏快路径**：EXIF 内嵌缩略图 + 两阶段渲染
- **格式/缓存快路径**：`IShellItemImageFactory`，优先吃 Explorer 缩略图缓存和 HEIC/RAW 系统解码器
- **回退路径**：现有 Go `image.Decode`
- **研究原型**：纯 Go JPEG DCT 缩放；只有通过决策门才进入默认路径

## 1. 现状与根因

| 环节 | macOS 原版 | 当前 Windows 版 |
|---|---|---|
| 解码 | ImageIO `CGImageSourceCreateThumbnailAtIndex`，`MaxPixelSize=512` | `image.Decode` 整图解码后再缩放 |
| 缓存 | `FileModel.image` + 默认 4GB 内存阈值；16 项去重缓存 | 420 张 bitmap + 1.5GB 磁盘 JPEG |
| 并发 | 本地 8，外接 1 | 固定 6；目录扫描最多 12 |
| 目录 | 渐进插入，readInfo 本地 2 / 外接 1 | `Browse` 等 `fillDims(900)` 跑完才返回 |
| UI | 只更新对应 item | 每张完成 `Invalidate()` 全窗 |

当前代码的关键事实：

- `thumb.go` 的 `renderThumb()`：`imageDims` → `os.Open` → `image.Decode` 整图 → `thumbnailImage` 面积平均 + Catmull-Rom → JPEG q84 编码写盘。
- worker 拿到 JPEG 字节后再 `ui.DecodeBitmap` 一次，冷路径是“整图解码 → 缩小 → 编码 → 解码”。
- `initThumbs()` 固定 `min(max(NumCPU,2),6)` 个槽；`thumb_queue.go` 已有可视区优先和过期任务丢弃，这部分不需要推翻。
- `dir.go` 的 `fillDims(list, 900)` 在 `Browse` 返回前同步执行；`probeImageDims` 每张图两次 open（`DecodeConfig` + `readExif` 读 128KB）。
- `thumbCacheMax=420` 按张数计数，不按字节；960 桶按 3:2 估算约 1GB。
- 每 150 次写缓存触发一次全目录 walk+sort 清理。
- `dir.go` 把 HEIC/RAW 列进 `imageExts`，注释说“decoding falls back to the shell”，但代码里没有真正的 Shell 缩略图实现；`renderThumb` 仍是 `image.Decode`，这些格式现在实际会走失败分支。

## 2. 目标与验收

### 2.1 性能目标（暂定，Phase 0 后按基线校准）

测试语料：真实 24MP JPEG，冷缓存，本地 NVMe；同时记录外接 USB HDD 和 SMB 网络盘。

| 场景 | 当前基线 | 目标 | 冲刺目标 |
|---|---:|---:|---:|
| 24 张 24MP 首屏 + 预取 20 张 | 约 2.12s | ≤ 1.0s | ≤ 0.7s |
| 100 张 24MP 冷加载完成 | 约 7s（线性外推） | ≤ 3.5s | ≤ 2.5s |
| 300 张 24MP 冷加载完成 | 约 20s（线性外推） | ≤ 10s | ≤ 7s |
| 首张可见卡片 | 未单独计时 | ≤ 300ms | ≤ 150ms |
| 快速滚动空白停留 p95 | 未单独计时 | ≤ 120ms | ≤ 80ms |
| 100 张 24MP 峰值内存 | 未单独计时 | ≤ 600MB | ≤ 450MB |

说明：当前 24MP 单张 322ms、24 张 1.68s 来自 v1.2.15 的合成渐变 JPEG，平均 7.8MB/张；真实 24MP 照片常见 10–20MB，磁盘压力更大，所以 Phase 0 必须用真实照片复测，不能直接拿旧数字当验收线。

### 2.2 质量与兼容目标

- EXIF Orientation 1–8 全部正确；透明 PNG 仍合成到中性卡片底色。
- 与当前缩略图对比，JPEG 平均通道误差 ≤ 2/255；不得出现明显光晕、色偏、过锐。
- JPEG baseline/progressive、CMYK、灰度、4:2:0/4:2:2/4:4:4 都能出图。
- PNG/APNG、GIF、WebP、TIFF、BMP、ICO 不回归。
- HEIC/HEIF、RAW（CR2/CR3/NEF/ARW/DNG/ORF/RW2/RAF/PEF/SRW）在系统装了对应解码器时能出图；没装时显示占位和明确状态，不崩溃。
- 损坏文件、0 字节、超大图（>150MP）走失败/占位分支，不拖垮队列。
- 视频缩略图链路不受影响。

## 4. Phase 0：基线与 profiling

### 4.1 计时埋点

在 `thumb.go` / `dir.go` / `app.go` / `grid.go` 增加仅在 `FLOWVISION_THUMB_PROFILE=1` 时启用的计时，不改变默认行为：

- 目录枚举：`ReadDir`、`Info`、排序
- `fillDims`：总耗时、单张 `probeImageDims` 耗时
- 队列：等待时间、运行时间、丢弃数量
- 缓存：`Stat`、`ReadFile`、命中/未命中
- 渲染：`image.Decode`、`areaScale`、Catmull-Rom、JPEG encode、写盘
- UI：`ui.DecodeBitmap`、`refresh` 次数、单次刷新耗时
- 内存：进程峰值、GC 次数、当前缓存字节

通过 debug 端点或日志输出 JSON 行，便于批量跑分。

### 4.2 语料来源与制作

语料采用“自制为主、下载为辅”：

- **自制**：用 Python 3.13 + Pillow 13 + numpy 生成，保证尺寸、EXIF、方向、格式、损坏场景都可重复；仓库只提交生成脚本和 `manifest.json`/`SHA256SUMS`，不提交大图。
- **下载**：只从明确 Public Domain / CC0 的公开图库补充真实照片纹理，逐文件在 `SOURCES.md` 记录来源和许可；不使用版权不明的高清样张。
- **存储**：本地放 `testdata/thumb-corpus`，加进 `.gitignore`；用 manifest 按 24/100/300 三档组目录，避免重复占用空间。
- **EXIF**：用 Pillow 写 IFD0 方向；IFD1 内嵌缩略图用自写 APP1/IFD1 注入（或安装 `piexif` 辅助），不依赖 exiftool。
- **高熵 24MP**：6000×4000，渐变 + 纹理 + 几何块 + 可控噪声，JPEG q90–92；避免纯渐变导致文件过小、跑分失真，目标 8–20MB/张。
- **300 张档**：用 24 张母图生成 300 个独立文件；本地 C 盘当前约 57.6GB 空闲，24MP×300 约 3GB，可承受。若空间紧张，降到 12MP 并记录换算。

语料清单：

- 24 张、100 张、300 张 24MP JPEG；一半带 EXIF 内嵌缩略图，一半不带。
- 12MP、24MP、48MP、100MP 各一组。
- baseline/progressive JPEG、CMYK JPEG、灰度 JPEG、4:2:0/4:2:2/4:4:4。
- 透明 PNG、16-bit PNG、GIF、WebP、TIFF、BMP、ICO。
- HEIC/HEIF、RAW 各若干（有系统 codec 和无 codec 两态）。
- EXIF Orientation 1–8、带 ICC、损坏文件、0 字节文件、权限拒绝文件。
- 下载的真实照片单独放 `real/`，自制片放 `synthetic/`，跑分报告分开列，避免合成图结论掩盖真实照片 I/O。

### 4.3 跑分矩阵

- 冷缓存：清空应用缩略图缓存；系统文件缓存用新拷贝或重启隔离。
- 热缓存：第二次打开同一目录。
- 存储：本地 NVMe、USB HDD、SMB 网络盘。
- 并发：4 / 6 / 8 worker。
- 尺寸：160 / 240 / 320 / 480 / 960 桶。
- 每项至少 3 次，记录中位数和 p95。

### 4.4 决策门 0

- 如果 `image.Decode` 占冷加载 < 40%，先做扫描/UI/缓存，WIC 仍然做但顺序后移。
- 如果 `fillDims` 或 UI 刷新占比 > 30%，Phase 1 必须先于 WIC 完成。
- 如果 24MP 真实照片单张 > 500ms，WIC 优先级最高。

## 5. Phase 1：低风险结构优化

这一阶段不改解码算法，先去掉明显的阻塞和浪费；作为 `v1.3.0` 的第一批提交，不单独发版。

### 5.1 单次 open 读取尺寸 + EXIF

- 重构 `probeImageDims`：JPEG 只 open 一次，读前 128KB，同时解析 SOF 尺寸和 EXIF；非 JPEG 回退 `image.DecodeConfig`。
- `readExif` 保留给信息面板，但复用同一套字节解析，避免重复打开。
- 目标：900 张图的 open 次数从约 1800 降到约 900，头读取不重复。

### 5.2 `fillDims` 首屏化

- `fillDims` 预算从 900 降到首屏 2–3 屏（约 160–240 张），其余由滚动触发懒加载。
- `Browse` 不再等待全部尺寸；列表先返回，尺寸后台补。
- 未知宽高的卡片先用 3:2 占位比例，尺寸到达后回流；记录并恢复滚动位置，避免跳动。
- 如果回流不可接受，保留 `Browse` 等首屏 160 张，剩余懒加载。

### 5.3 批量 UI 刷新

- 把 `thumbWorker` 每张完成就 `a.refresh()` 改成 dirty set + 33–50ms 合并刷新。
- 只对当前可见 key 触发重绘；不可见完成只更新缓存。
- 队列清空或窗口关闭时强制 flush 一次。
- 目标：减少全窗 `Invalidate`/布局次数，滚动更稳。

### 5.4 按字节的内存缓存

- `thumbEntry` 增加 `Bytes`，`thumbCacheMax` 从 420 张改为字节预算，默认 256MB。
- 240 桶可以多留，960 桶自动少留；淘汰时 `ReleasePixels()`。
- 访问时更新 LRU 顺序，不再只按插入顺序。
- 保留磁盘 JPEG 缓存；不要为了省内存改成 PNG/RAW，PNG 解码更慢。

### 5.5 缓存清理

- 用运行总量代替每 150 次全目录 walk；清理改到空闲时或低频定时。
- 清理时避免与 worker 抢磁盘；可先删最旧 20%，不做全量排序。
- 磁盘缓存上限仍按设置里的 `CacheLimitMB`。

### 5.6 Phase 1 验收

- 目录首屏出现时间下降；首张缩略图不再等 900 张头扫描。
- 滚动时全窗刷新次数明显下降。
- 240/960 桶内存不再随张数失控。
- 缩略图质量与当前一致；所有现有测试通过。

## 6. Phase 2：WIC / Shell 后端

### 6.1 Spike（先不接 UI）

新增一个独立 spike 程序或 `thumb_wic_spike_test.go`，对同一批 24MP JPEG 比较：

- 当前 `renderThumb` 全解码
- WIC `IWICBitmapSourceTransform` 缩放解码（1/8、1/4、1/2）
- WIC `IWICBitmapScaler` 高质量 cubic
- `IShellItemImageFactory::GetImage`

记录：单张耗时、峰值内存、输出质量、方向、透明、失败率。每个路径至少 20 张，160/320/960 三个目标尺寸。

### 6.2 后端接口

新增 `thumb_backend.go`：

- `type thumbBackend interface { Render(ctx, item, size, opts) (image.Image, error) }`
- `thumbBackendKind`：`auto` / `wic` / `shell` / `go` / `embedded`
- `selectBackend(ext, item)`：JPEG 优先 WIC；HEIC/RAW 优先 Shell/WIC；WebP/异常格式回退 Go。
- `renderThumb` 改为“后端返回 image，pipeline 统一编码/缓存”，避免每个后端各自写 JPEG。
- 回退链：embedded → WIC → Shell → Go → placeholder；每层有超时/错误上限，避免循环。

### 6.3 WIC 实现

新增 `thumb_wic_windows.go`（Windows build tag）：

- `CoInitializeEx` 在每个 worker goroutine 初始化；优先 MTA，避免 STA 消息泵。
- `CoCreateInstance` 创建 `IWICImagingFactory`；每 worker 复用一个 factory，任务结束释放 decoder/frame/transform。
- `CreateDecoderFromFilename` → `GetFrame(0)` → `GetSize`。
- JPEG 查询 `IWICBitmapSourceTransform`：
  - `GetClosestSize` 获取支持的缩放尺寸
  - `CopyPixels` 直接输出目标附近尺寸的 32bpp RGBA
  - 用 `WICBitmapTransformOptions` 或 `IWICBitmapFlipRotator` 处理 EXIF 方向
- 没有 transform 的格式用 `IWICBitmapScaler`，`WICInterpolationModeHighQualityCubic`。
- 输出统一转 `image.NRGBA`，预乘 alpha，再合成到现有中性底色。
- HRESULT 转 error；每个任务 `recover()`，绝不让 COM 异常带崩 UI。
- `runtime.KeepAlive` 保证 COM 对象生命周期。

### 6.4 Shell 快路径

新增 `thumb_shell_windows.go`：

- `SHCreateItemFromParsingName` → `IShellItemImageFactory` → `GetImage`。
- 标志：`SIIGBF_THUMBNAILONLY | SIIGBF_BIGGERSIZEOK | SIIGBF_RESIZETOFIT`。
- `HBITMAP` 用 `GetDIBits` 转 32bpp BGRA；透明/背景按当前卡片底色处理。
- 用途：HEIC/RAW 系统 codec、WIC 失败、Explorer 缓存已热的目录；不作为 JPEG 默认路径，避免依赖 Shell provider 的不确定性。
- 调用放在 worker 内，不占 UI 线程；失败立即回退。

### 6.5 缓存与版本

- 磁盘缓存文件名加入后端版本，例如 `...-<Mtime>-<Size>-<backend>-v2.jpg`，避免旧 q84 缓存掩盖新路径。
- 只缓存最终图；preview 不落盘。
- 旧缓存可以保留一个版本周期，确认无回滚需求后清理。
- 缓存键仍包含源文件 Mtime/Size，源文件变更必须失效。

### 6.6 Phase 2 验收

- 24MP JPEG 冷加载相对当前提升 ≥ 1.8x，目标 2–5x；质量不下降。
- 100/300 张目录的完成时间达到 Phase 0 校准后的目标。
- WIC 失败、无 codec、损坏文件都能在 1 次回退内出占位，不崩溃。
- HEIC/RAW 在系统 codec 可用时能出图。
- COM 对象无泄漏；连续滚动 10 轮内存不持续上涨。

## 7. Phase 3：EXIF 内嵌 + 两阶段渲染

### 7.1 IFD1 内嵌缩略图

- 扩展 `meta.go` 的 EXIF 解析：从 IFD0 的 next IFD 进入 IFD1，读取 `0x0201`（JPEGInterchangeFormat）和 `0x0202`（length）。
- 校验 offset/length 在文件范围内，长度上限 2MB；只接受 JPEG 压缩（`0x0103=6`）。
- 读出内嵌 JPEG 并解码；应用 IFD0 的 Orientation。
- 判定：
  - 内嵌尺寸 ≥ 目标桶的 0.75x：可直接作为 preview，甚至小桶（≤320）的最终图。
  - 小于目标：只做 preview 占位，最终图仍走 WIC/Go。
  - 没有内嵌：跳过，不产生额外 I/O。
- 结果按 item + mtime 缓存在内存；源文件变更失效。

### 7.2 两阶段渲染

- `thumbTask` 增加 `stage`（preview/final）和 `generation`。
- 网格优先请求 preview（96/160），高优先级；final 随后入队，低优先级。
- preview 来源：内嵌缩略图 → WIC 160 → Go 160；失败则先用纯色/文件名占位。
- final 到达后替换 preview；如果用户已滚出视口，丢弃结果但不写缓存。
- 同一卡片尺寸变化时，旧 final 保留到新 final 完成，避免闪白。
- preview 不进入磁盘缓存，避免污染最终缓存。

### 7.3 视觉与交互

- preview 允许轻微模糊，但不能有色偏/拉伸；用现有中性底色。
- 最终图替换时不做大动画，直接换图，避免闪烁。
- 卡片文件名、选中态、视频角标不因 preview/final 切换而跳动。

### 7.4 Phase 3 验收

- 24MP 首张可见 ≤ 300ms；有内嵌缩略图的相机 JPEG 首屏明显更快。
- 最终图质量与 Phase 2 一致；没有“低清图被当成最终图”的情况。
- 快速滚动不出现 preview 队列压住 final 队列；final 仍能在合理时间内完成。
- 无内嵌缩略图的图片不会被额外拖慢。

## 8. Phase 4：纯 Go JPEG DCT 缩放原型

这一阶段是研究/备选，不默认进入生产；满足决策门才接入。

### 8.1 原型范围

- 新建 `internal/jpegscale` 或 `thumb_dct.go`，不直接改 `image/jpeg` 标准库。
- 第一版只支持 baseline sequential JPEG、4:2:0/4:2:2/4:4:4、无 restart 或简单 restart。
- 先做 1/8：只取每个 8×8 块的 DC，输出 1/8 尺寸；这是成本最低、收益最明显的档位。
- 第二版做 1/4（2×2 IDCT）和 1/2（4×4 IDCT）。
- progressive JPEG、复杂 restart、CMYK 第一版回退现有全解码；后续再评估。

### 8.2 质量与性能

- 与 WIC、当前 Go 全解码对比：单张耗时、峰值内存、SSIM/通道误差、文字/细线边缘。
- 目标：1/8 解码相对全解码 ≥ 3x；1/4 ≥ 2x；质量不低于 WIC 同尺寸。
- 如果 WIC 已经稳定达到目标，DCT 只作为无 COM/无系统 codec 环境的回退，不抢默认路径。

### 8.3 决策门 4

- DCT 相对 WIC 没有 ≥ 1.5x 优势，或方向/渐进式/CMYK 质量不过关：归档，不进入默认路径。
- WIC 因环境/打包/稳定性不可用：DCT 作为 JPEG 主回退。
- 任何情况下保留现有 `image.Decode` 作为最后回退。

## 9. Phase 5：格式、质量、稳定性回归

### 9.1 格式矩阵

| 格式 | 默认后端 | 回退 | 必测点 |
|---|---|---|---|
| JPEG baseline | WIC transform | Go | 方向、CMYK、灰度、4:2:0/4:2:2/4:4:4 |
| JPEG progressive | WIC / Go | Go | 渐进扫描、方向 |
| PNG/APNG | WIC | Go | alpha、16-bit、透明底 |
| GIF | Go/WIC | Go | 首帧、动画角标 |
| WebP | WIC（若支持）/Go | Go | 有损/无损、alpha |
| TIFF/BMP/ICO | WIC/Go | Go | 多页/位深/图标 |
| HEIC/HEIF | Shell/WIC | 占位 | 系统 codec 有无两态 |
| RAW | Shell/WIC | 占位 | 内嵌预览、方向、无 codec |

### 9.2 质量回归

- 20 张真实图片，当前 vs 新路径并排对比；记录平均通道误差、边缘、肤色、天空渐变。
- 透明 PNG 合成到 `#2a2a2e` 底色，检查边缘黑边/白边。
- 广色域/ICC 图片检查是否明显偏色；WIC 色彩管理若与当前差异大，统一切到 sRGB 输出。
- 旋转 1–8 各一张，检查宽高和方向。

### 9.3 稳定性

- 连续滚动 10 轮、快速切换 20 个目录、打开 300 张目录后关闭。
- 监控 COM 对象、GDI 对象、goroutine、内存；不得持续上涨。
- 损坏/0 字节/权限拒绝/文件被占用：占位、日志、不崩溃。
- 外接盘拔出、网络盘断开：任务失败回退，不卡队列。

## 13. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| COM 线程/套间错误 | 崩溃/卡死 | 每 worker 初始化；MTA 优先；recover；失败回退 |
| WIC 格式覆盖不足 | HEIC/RAW/WebP 失败 | Shell/Go 回退；占位；格式矩阵 |
| 色彩/方向/透明差异 | 视觉回归 | 统一 RGBA/sRGB；方向测试；透明底回归 |
| 缓存旧数据 | 新路径被旧 JPEG 掩盖 | 缓存键加 backend/version；旧缓存清理 |
| 两阶段闪烁 | 体验变差 | generation token；旧 final 保留到新 final；不做动画 |
| 目录回流 | 滚动跳动 | 首屏 160 张同步；其余懒加载；记录滚动位置 |
| DCT 维护成本 | 长期负担 | 只做原型；决策门；不默认启用 |
| 性能测试噪声 | 误判 | 固定语料/机器；3 次中位数；冷/热分离 |
| Shell 调用阻塞 | worker 卡住 | 独立 worker；超时/失败回退；不占 UI 线程 |

## 15. 决策门汇总

- **Gate 0**：Phase 0 后确认瓶颈占比；decode < 40% 时先做扫描/UI。
- **Gate 1**：WIC spike 相对当前 ≥ 1.8x 且质量通过，才接入默认路径；否则 WIC 只用于格式覆盖。
- **Gate 2**：两阶段首屏提升 ≥ 30% 且无闪烁/回流投诉，才默认开启；否则只保留内嵌缩略图快路径。
- **Gate 3**：DCT 相对 WIC ≥ 1.5x 或 WIC 不可用，才进入默认/回退路径；否则归档。
- **Gate 4**：Phase 5 全矩阵通过、性能达标、无内存/GDI/COM 泄漏，才发布。
