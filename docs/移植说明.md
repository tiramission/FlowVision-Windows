# 移植说明：从 Swift/AppKit 到 Go + MyGo

本文记录评估依据、模块对照、关键算法迁移方式和在 Windows 上踩到的坑，便于后续维护或继续补齐功能。

## 1. 为什么不是“改造”，而是重写

原仓库 `FlowVision/Sources` 的实测统计（用文件扫描 + 文本计数得到）：

- 54 个 `.swift` 文件，合计 33,088 行；另有 `Main.storyboard`（113 KB）、6 个 XIB、`.xcstrings` 本地化资源。
- `NSView` / `NSWindow` / `NSControl` 等 AppKit 类型共出现 1,427 次；`import AppKit` 出现 54 次（几乎每个文件）。
- CoreGraphics 366 次、FileManager 92 次、ImageIO 49 次、xattr/Finder 标签 22 次、AVFoundation 21 次、FSEvents/DispatchSource 18 次、CoreImage 11 次。
- `Metal`、`vImage`、`QuickLook` 均为 0 次 —— 原项目没有自绘 GPU 管线，图片缩放/合成都交给 CoreGraphics。

由此得到三个判断：

1. **AppKit 视图层无法在 Windows 上复用**：`NSCollectionView` + 自定义 `NSCollectionViewLayout` + `NSViewController` 的组合没有跨平台实现，按行翻译的成本高于用 Web 重画。
2. **平台 API 需要等价替换或降级**：HDR（`preferredImageDynamicRange`）、Finder 标签（xattr）、全局 `NSEvent` 监听、QuickLook 在 Windows 上没有对应 API。
3. **纯逻辑可以原样迁移**：瀑布流排版、自然排序、缩略图缓存、EXIF、导航、手势方向、快捷键，这些与原项目逐段对照后搬到了 Go/JS。

最终架构：

```
┌────────────────────────────── FlowVision.exe（Go，无 cgo）──────────────────────────────┐
│  main.go      窗口/菜单/服务绑定/启动路径     menu.go   原生菜单 → 异步 Eval("window.fv.menu()") │
│  dir.go       扫描、排序、Tree/Sibling/Parent  thumb.go  缩略图 + 磁盘缓存 + ffmpeg 取帧    │
│  meta.go      尺寸、EXIF、MediaSvc             media.go  img:// 协议 + 回环视频流            │
│  settings.go  Settings/Prefs                   actions.go 对话框、文件操作、退出             │
│  win32.go     隐藏属性、SHFileOperationW 回收站                                              │
│                    ▲ mygo.Bind（JSON-RPC）           ▲ 自定义 scheme / loopback HTTP          │
│                    │                                  │                                      │
│  web/index.html + style.css + app.js  ◄──── WebView2（页面 origin http://mygo.localhost）     │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 3. 关键算法

### 3.1 瀑布流（对应 `Layout.swift` 的 `CustomFlowLayout`）

原实现：行高固定，宽度按图片宽高比计算，行内从左到右排列，放不下就换行，行高取该行最大高度。移植为：

```js
const rowH = clamp(settings.thumbSize, 110, 460);
const gap  = clamp(settings.gridGap, 0, 30);
let x = 0, y = 0;
for (const item of view) {
  const ar = clamp(item.w / item.h || 1, 0.34, 3.2);
  const w  = Math.round(rowH * ar);
  if (x > 0 && x + w > width) { x = 0; y += rowH + gap; }
  positions.push({ x, y, w, h: rowH });
  x += w + gap;
}
```

- 行高固定后，行内最大高度就是行高，所以 `rowMax` 可以省略。
- 缩略图未返回尺寸时按 1:1 占位；`img.onload` 补上真实宽高后 260 ms 防抖重排，并保持视口顶部项不跳。
- 虚拟化：只创建视口上下各 800 px 内的 tile，其余用绝对定位占位高度撑开滚动条。

### 3.2 缩略图缓存（对应 `ImageProcess` 的缩放与缓存）

- 缓存键：`<md5(path)[:14]>-<bucket>-<mtime>-<size>.jpg`，bucket 为 96/160/240/320/480/640/800/960（按 CSS 宽度 × DPR 选桶）；把源文件 mtime 和大小写进文件名，避免同秒内替换文件后复用旧缩略图。
- 失效条件：缓存文件 mtime 小于源文件 mtime，或大小为 0；源文件尺寸或 mtime 变化会生成新缓存名。
- 生成：EXIF 方向先校正 → `draw.CatmullRom.Scale` → 透明区域合成 `#2a2a2e` → JPEG q84。
- 并发：`chan struct{}` 信号量，槽位数 `min(max(NumCPU,2),6)`，避免 4K 图片批量解码打满 CPU。
- 视频帧：`ffmpeg -ss 0.6 -frames:v 1 -vf scale=-2:<size> -f image2pipe -vcodec mjpeg`；找不到 ffmpeg 就画渐变 + 播放三角占位图。
- 预览图：TIFF 等 WebView2 不能直接解码的格式按需转 2,560px JPEG，缓存名为 `<id>-preview-<mtime>-<size>.jpg`，并用互斥锁串行化解码，避免一屏 TIFF 同时展开占用内存。
- 淘汰：累计写入每 150 次触发一次，按访问时间（`Chtimes`）最旧优先删除，直到低于 `CacheLimitMB` 的 80%。

### 3.3 EXIF 方向

手写 TIFF IFD 解析（`meta.go`）：JPEG 的 APP1 → TIFF 头（II/MM）→ IFD0 标签 `0x0112`。读取方向后交换宽高（5–8 需要旋转 90°），缩略图渲染时再按方向做像素变换。EXIF 展示字段：厂商 `0x010F`、机型 `0x0110`、拍摄时间 `0x9003`、曝光 `0x829A`、光圈 `0x829D`、ISO `0x8827`、焦距 `0x920A`、镜头 `0xA434`、35mm 等效 `0xA405`、曝光补偿 `0x9204`、测光 `0x9207`、色彩空间 `0xA001`。

### 3.4 同级文件夹跳转（对应原项目的“下一个有图片的文件夹”）

`FS.Sibling(path, ±1, showHidden)`：读父目录，按名称排序后从当前文件夹的位置向一个方向线性查找，跳过隐藏目录，用 5 秒的 `mediaCache` 缓存“该目录是否含媒体”，避免每次导航都递归扫盘；到边界返回 `found=false`。`showHidden` 由页面显式传入，不再读取可能滞后于前端设置的持久化配置。

## 4. Windows / MyGo 实测坑

1. **自定义 scheme 在 Windows 上必须写成 http 形式。**
   `img://localhost/x.png` 在 `<img>` 中加载失败（`naturalWidth=0`）；改成 `http://img.localhost/x.png` 后返回 200。前端因此按 `location.origin` 判断：
   ```js
   const IMG_ORIGIN = location.origin === "http://mygo.localhost"
     ? "http://img.localhost" : "img://localhost";
   ```
2. **`mygo.Bind` 的方法签名只允许 `(args...)` 或 `(args...) (T, error)`。**
   `func (FS) Exists(path string) (bool, string)` 会在启动时 panic：`the second result must be an error`。改成返回结构体 `ExistsResult{OK,Path}`。
3. **模块代理**：`proxy.golang.org` 在本机 TLS 超时，必须 `GOPROXY=https://goproxy.cn,direct`；`golang.org/x/sys` 拉不下来，于是隐藏属性判断改用标准库 `syscall.GetFileAttributes`，回收站用自建 `shFileOpStruct`（注意 64 位对齐）。
4. **`Page().Eval` 返回 `(any, error)`**，不能直接断言成 string；日志里要 `%v`。
5. **WebView2 编解码**：H.264/VP9 通常可用，HEVC/MKV 视系统扩展而定；后端标记 `play`，前端对不可播放容器回退到“系统播放器打开”。
6. **窗口首帧白屏**：`Hidden: true` + `OnReadyToShow(win.Show)`，配合 `BackgroundColor: "light-dark(...)"`，页面 ready 后再显示。
7. **不要在 WebView 的键事件回调里同步 `Page().Eval`。** 原生菜单的 `Accelerator` 由 WebView2 的 accelerator-key 事件分发；`Page().Eval` 的内部实现是 `w.do(...)`（投递到 UI 线程）再等待页面 Promise 完成。若在按键回调里直接调用，UI 线程会被自己投递的任务卡住，表现为按下 Ctrl+W 后整个页面和调试端点一起失去响应，直到 eval 超时。修复：菜单动作统一 `go evalPage(...)` 异步派发；`OnReadyToShow`、`OnSecondInstance` 里打开路径也同样异步。修复后实测 Ctrl+T/W/O/B/R/+/−、Ctrl+Left/Right 均只触发一次且页面不卡死。
8. **单实例第二次启动**：`OnSecondInstance` 回调只负责把路径转成文件夹并异步 `openPath`，窗口尚未创建时先存入 `pendingOpen`，等 `OnReadyToShow` 再打开。
9. **原生菜单与页面快捷键会重复触发吗？** WebView2 的 accelerator 事件设置 `Handled=1` 后不再进入页面 keydown；实测按一次 Ctrl+W 只关一个标签。页面的 keydown 保留给没有 accelerator 的按键（方向键、Delete、F2 等）。

## 6. 后续可以补的点

- 缩略图内存 LRU（目前只做磁盘缓存，快速滚动会重复读盘）。
- 视频缩略图内置解码（需要引入纯 Go 的 MP4/H.264 解析，代价较大）。
- 多选批量重命名、拖拽移动文件。
- 侧边栏树自动展开到当前路径（目前只高亮已知节点）。
- 文件夹变更监听（`ReadDirectoryChangesW`）做自动刷新。
